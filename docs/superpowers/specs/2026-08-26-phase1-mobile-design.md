# BCN Restaurant Mobile Phase 1 Design

## Goal
Build a production-oriented foundation for a single Flutter restaurant app backed by a Git-controlled Frappe/ERPNext v16 custom app. Phase 1 covers authentication, role/bootstrap data, dine-in/takeaway table selection, menu loading, cart management, and idempotent Sales Order creation/submission.

## Existing ERPNext Model
The existing site uses standard Sales Order as the restaurant KOT/order transaction. Items already carry `custom_kitchen_counter`, Sales Order Item carries preparation fields, Product Bundle expands recipe ingredients, and Kitchen Counter routes lines to counter warehouses. This design preserves that model rather than introducing a competing Restaurant Order DocType.

## Architecture
The repository is a monorepo:

- Repository root (`pyproject.toml` + `bcn_restaurant/`): Frappe v16 custom app installed on the ERPNext site/Frappe Cloud.
- `mobile/bcn_restaurant_mobile`: Flutter app used by waiter/kitchen/cashier/manager roles.
- `docs`: architecture, API, installation, and implementation notes.

Flutter never writes generic ERPNext documents directly. It calls whitelisted custom endpoints. The server resolves prices, kitchen counter, warehouse, company, price list, and authorization.

## Phase 1 Backend Components

### Restaurant Settings
A Single DocType centralizes site-specific names:
- Company: `BCN Restaurant`
- POS Profile: `BCN Restaurant POS`
- Selling Price List: `Restaurant Menu Price`
- Dine In Customer Group: `Dine In`
- Takeaway Customer Group: `Takeaway`
- Default Currency: `MMK`

### Restaurant Table Session
A lightweight session groups multiple Sales Orders for one table/takeaway visit while keeping each Sales Order as a separate KOT batch.
Fields:
- customer
- customer_group
- waiter
- opened_at
- status: Open / Billing / Paid / Closed / Cancelled
- guest_count
- closed_at

Phase 1 creates/reuses an Open session. Consolidated billing is intentionally deferred to the cashier phase.

### Sales Order Custom Fields
The app creates:
- `custom_restaurant_session` Link → Restaurant Table Session
- `custom_client_order_id` Data, unique

`custom_client_order_id` is a UUID generated by Flutter. Repeated mobile requests return the existing order instead of creating duplicates.

### API Endpoints
- `bcn_restaurant.api.bootstrap.get_bootstrap`
- `bcn_restaurant.api.tables.get_tables`
- `bcn_restaurant.api.menu.get_menu`
- `bcn_restaurant.api.orders.create_order`

Frappe's standard `/api/method/login` and `/api/method/logout` are used for session authentication.

### Server-side Order Rules
The client may send only:
- customer
- session (optional)
- client_order_id
- remarks (optional)
- item_code
- qty
- uom (optional)
- kitchen_note (optional)

The server validates the role, customer group, active menu item, positive quantity, and current price. The server assigns kitchen counter and warehouse from Item/Kitchen Counter and sets preparation status to New. The Sales Order is inserted and submitted by the API.

### Date Filtering
Phase 1 table/session/order retrieval is limited to active sessions/current operational context. Existing old Sales Orders are not treated as current table state merely because they remain unbilled.

## Flutter Architecture
Feature-first structure:
- `core/config`: base URL via `--dart-define=BASE_URL`
- `core/network`: Dio client, session cookie handling
- `core/storage`: secure SID storage
- `features/auth`: login state and screen
- `features/bootstrap`: role/profile bootstrap
- `features/waiter`: table selection and order flow
- `features/menu`: menu models/repository/screen
- `features/cart`: cart state
- `features/orders`: create-order repository and result screen

State management uses Riverpod. Navigation uses go_router. Session ID is stored with flutter_secure_storage. HTTP uses Dio.

## Authentication
The app posts username/password to `/api/method/login`. It extracts the `sid` cookie from response headers and stores only the SID in secure storage. Subsequent requests send `Cookie: sid=<value>`. Passwords are never persisted.

## Error Handling
Backend validation errors use `frappe.throw` with clear user-facing messages. Flutter maps network/HTTP/Frappe errors to concise messages. Place Order is disabled while a request is in flight. Because each request contains `client_order_id`, retry after timeout is safe.

## Testing
Pure backend input normalization/validation logic has fast pytest tests independent of a running bench. Frappe integration tests are included for execution inside a v16 bench. Flutter includes model/cart tests and a login/session parsing test. Where Flutter SDK is unavailable in the build environment, those tests remain runnable on the user's Flutter machine.

## Deployment Constraint
The current production/demo site still contains Restaurant Server Scripts. The custom app can coexist during migration, but overlapping order-routing/create-order scripts should be disabled only after the app endpoint is tested on a staging site. No API secret is embedded in Flutter.

## Deferred Beyond Phase 1
- Kitchen queue/actions and realtime
- Waiter Ready/Serve actions
- Consolidated session Sales Invoice
- Cash/Kpay payment and change calculation
- Automatic Delivery Note submission/stock posting
- Manager dashboard/exceptions
- Shift DocType and shift open/close UI
- Full offline ordering


## Repository Deployment Layout Decision
The Frappe app is rooted at the Git repository root rather than under `backend/`. This is deliberate so Bench/Frappe Cloud can clone the GitHub repository and immediately recognize `pyproject.toml` and the `bcn_restaurant` package. The Flutter project remains an extra subdirectory and is not part of the Python package.
